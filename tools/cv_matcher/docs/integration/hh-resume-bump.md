## Поток и границы

Web «Сегодня» / Telegram «Система и настройки → Поднятие резюме HH» → [resume_bump.py](../../src/resume_bump.py) → `settings` / `browser_commands` существующей SQLite → [hh-workflow.js](../../hh-research-extension/hh-workflow.js) → [resume-bump-worker.js](../../hh-research-extension/resume-bump-worker.js) → [resume-bump-content.js](../../hh-research-extension/resume-bump-content.js) → receipt → общий outbox Telegram.

- Policy: enabled, список source HH IDs, revision. Изначально disabled. Сохранение enabled требует точного действия пользователя; Telegram permission привязан к ID, revision и TTL 15 минут. Веб позволяет несколько CV, Telegram — основное CV и паузу существующей настройки. Чужой Telegram account игнорируется прежним owner guard.
- `hh_auto_sync.run` вызывает атомарный scheduler tick; новые процессы и БД не добавлялись. При отсутствии Chrome создаётся одна очередь на CV, которую переживают перезапуски. Старый executor без явного kind `resume_bump` её не получает.
- Перед записью выполняется token-only `resume_bump_claim`. Текущая policy/version проверяется повторно; claim однократный и сохраняется до UI-клика. Проверяется профиль `https://hh.ru/applicant/profile/me`, точный выбранный resume ID и однозначная карточка. Импорт по ссылке не является доказательством владения: CV обязан присутствовать в личном профиле Chrome.
- В 0.11.18 учтены карточки с button-заголовком, где ID находится в соседнем `search/vacancy?resume=…` link, и controls с role=link. Ожидания Chrome API/claim ограничены 15 сек, закрытие временной вкладки — 5 сек. Новую команду получает только executor с `resume_bump_version=1`; ранняя 0.11.17 без этого handshake больше её не забирает. Первопричина потери первого receipt не доказана; эти изменения покрывают выявленные риски DOM и неограниченного ожидания. Повтор после первого claim разрешается только владельцем после сверки.
- Только точная бесплатная кнопка; «Сделать видимым», неопубликованные CV, services/payment/premium, неоднозначность и диалоги/CAPTCHA останавливают исполнение. Не подключаются платные услуги. Текст/видимость CV не редактируется.
- Подтверждение: после одного клика в той же карточке появляется cooldown / недоступная кнопка. Затем next_at ≥ last_success + 4h. Пока кнопка недоступна до claim — новая read-only проверка через 15 минут. При неопределённом результате повтор запрещён до «Проверил результат на HH — разрешить новую проверку».
- При сбое после claim нет повторного клика после MV3 restart; receipt сохраняется существующим `wfSaveReceipt`. Старый running без claim можно вернуть в очередь; claimed → uncertain. Отмена queued-задачи блокирует автоматическое пересоздание для этого CV.
- Завершение и ошибки идут через существующий `workflow_delivery`, без отдельного Telegram-агента. Статус есть в `/status`, общей очереди и Web. Нейтральные cooldown-проверки не рассылаются.

## API

Существующий POST `/archive/workflow`: `resume_bump` (status), `resume_bump_save` (config/revision/confirmed), `resume_bump_retry` (resume_id/confirmed), `resume_bump_claim` (command_id/worker_id, только токен расширения). Результат идёт через прежний `result` с kind-aware проверкой. Авторизация cookie/Origin и token не ослаблялась.

## Проверки

350 Python / 318 JS успешно на текущем срезе. Новые [Python tests](../../src/tests/test_resume_bump.py) и [JS fixtures](../../hh-research-extension/resume-bump.test.mjs) покрывают выбор, подтверждение, атомарность, restart, cooldown, owner/revision, поддельную/просроченную форму, скрытую карточку, отказ claim и uncertain. Настройка Web проверена через живой API и accessibility Chrome. Начальный executor передал heartbeat/claim, но успешного live receipt нет. Исправленная 0.11.18 требует перезагрузки существующего расширения. Пользователь сознательно оставил включение себе.

Автоотклики используют прежний отдельный approval workflow. Рассылка по всем вакансиям без согласования не добавлялась; для компаний всё ещё нет универсального автоматического submit.

HH описывает бесплатное поднятие не чаще раза в четыре часа: [база знаний HH](https://feedback.hh.ru/knowledge-base/article/0012145). Состояние реальной кнопки имеет приоритет над локальным расписанием.
