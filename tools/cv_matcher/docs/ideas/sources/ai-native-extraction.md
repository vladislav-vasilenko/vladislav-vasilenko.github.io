**Да. Более того, я считаю, что переход к AI-native архитектуре — одно из наиболее перспективных направлений развития твоего сервиса.** Но я бы не заменял существующий краулер полноценным браузерным агентом. Я бы построил **гибридную систему с автономным AI-агентом, способным самостоятельно обнаруживать, анализировать и обрабатывать вакансии на различных карьерных платформах.**

Идея принципиально отличается от обычного веб-скрапинга.

Сейчас твоя система зависит от реализации конкретных сайтов:

```text
hh.ru
  └── HTML / DOM
       └── CSS selectors
            └── Vacancy Parser
                 └── Structured Vacancy
```

Если HeadHunter изменит структуру DOM или названия атрибутов, отдельные этапы сбора данных могут перестать работать.

Ты предлагаешь перейти к другой парадигме:

```text
Career Website
      │
      ▼
AI Browser Agent
      │
      ├── Understand Page
      ├── Discover Vacancies
      ├── Navigate Website
      ├── Extract Structured Data
      ├── Validate Results
      └── Adapt to UI Changes
      │
      ▼
Unified Vacancy Database
      │
      ▼
Personalized Career Intelligence
```

Это уже не просто парсер, а **агент, работающий с веб-сайтом на уровне пользовательских задач**.

Например, вместо инструкции:

`Найди div с определённым CSS-классом и извлеки текст`

ты формулируешь задачу:

> Найди все актуальные вакансии, связанные с LLM Pretraining, Generative AI и Deep Learning Research, опубликованные Яндексом за последние семь дней. Извлеки требования, специализацию, команду, условия работы и ссылки.

Агент самостоятельно определяет, как выполнить её на конкретном сайте.

Однако здесь есть архитектурная ловушка: **LLM-агент не гарантирует устойчивости к изменениям интерфейса**. Он менее зависим от CSS, но зависит от доступности страницы, качества её семантической структуры, возможностей браузерного управления и собственной точности.

Поэтому оптимальное решение — не *LLM вместо парсера*, а **детерминированный сбор данных с интеллектуальным механизмом восстановления и выполнения сложных действий**.

## 1. Какую архитектуру я бы выбрал

Я бы построил систему по принципу **API-first, Agent-assisted**.

| Уровень | Механизм | Когда использовать |
|---|---|---|
| 1 | Official API | Если площадка предоставляет подходящие методы |
| 2 | Structured Data Extraction | Если вакансии представлены в JSON-LD или другом структурированном формате |
| 3 | Semantic DOM Extraction | Если данные доступны только через HTML |
| 4 | AI Browser Agent | Если требуется интерактивная навигация или стандартный извлекатель перестал работать |
| 5 | Visual Computer Use | Если DOM недостаточен и необходимо взаимодействовать с визуальным интерфейсом |

**Почему именно такая последовательность?**

Потому что каждый следующий уровень, как правило, требует больше вычислений, времени и сложнее поддаётся проверке.

### HeadHunter: здесь уже существует API

Я проверил официальную [документацию HeadHunter API](https://api.hh.ru/openapi/redoc).

У HH есть методы поиска вакансий и получения данных в JSON. Предусмотрены OAuth2 и ограничения доступа; документация также описывает особенности поиска, включая ограничение глубины выдачи и возможную капчу без авторизации. [api.hh.ru](https://api.hh.ru/openapi/redoc?utm_source=chatgpt.com)

Следовательно, для HH я бы прежде всего исследовал возможность перенести поиск и извлечение описаний на официальный API.

Это потенциально позволит отказаться от значительной части CSS-парсеров.

Но не все пользовательские действия обязательно доступны через API в нужном режиме. Например, процессы отправки отклика и заполнения дополнительных форм необходимо исследовать отдельно.

### Яндекс, Сбер, Ozon, Авито, Самокат

Здесь я бы начал с технического аудита карьерных сайтов.

Важный момент: **сам факт отсутствия публичного API ещё не означает необходимость использовать AI Browser Agent**.

Многие сайты публикуют данные через структурированную разметку `schema.org/JobPosting`. Она может содержать название должности, описание, работодателя, дату публикации, местоположение и другую информацию. Google официально поддерживает такой формат. [Google for Developers](https://developers.google.com/search/docs/appearance/structured-data/job-posting?utm_source=chatgpt.com)

Другие сайты загружают данные через внутренние JSON-ответы или серверный рендеринг.

Использование таких источников нужно проверять на соответствие условиям конкретного сайта. Не стоит считать внутренние endpoint'ы публичным API.

## 2. Самое интересное — Self-Healing Browser Agent

Это компонент, который я рекомендовал бы разработать в первую очередь.

Представим, что Яндекс обновил карьерный сайт.

Существующий CSS-парсер перестал находить карточки вакансий.

**В традиционной архитектуре:**

Парсер выдаёт ошибку → разработчик исследует DOM → обновляет селекторы → выпускает исправление.

**В предлагаемой архитектуре:**

```text
Vacancy Extractor
       │
       ▼
Extraction Validation
       │
       ├── SUCCESS ─────► Save Vacancies
       │
       └── FAILED
              │
              ▼
       Recovery Agent
              │
              ├── Inspect DOM
              ├── Inspect Accessibility Tree
              ├── Identify Semantic Elements
              ├── Attempt Extraction
              └── Validate Structured Output
                       │
                       ▼
                Recovery Successful?
                       │
                ┌──────┴──────┐
                │             │
               YES            NO
                │             │
                ▼             ▼
          Save Result     Human Review
          Propose Fix
```

В случае успешного восстановления агент сохраняет результат и предлагает новую конфигурацию извлечения.

Но автоматически внедрять исправление без тестирования я бы не разрешал.

Например, агент может успешно найти 10 вакансий, хотя на странице их 40. Формально результат будет валидным JSON, но фактически ты потеряешь 75% данных.

Поэтому важно проверять не только формат, но и **полноту извлечения**.

### Как минимизировать зависимость от CSS

Здесь полезен Playwright.

Вместо:

```python
page.locator("div.vacancy-card > div:nth-child(2)")
```

можно использовать семантические локаторы:

```python
page.get_by_role("link", name="ML Engineer")
```

Такие локаторы опираются на доступные пользователю роли и названия элементов, а не на их положение в DOM. Playwright официально рекомендует их для повышения устойчивости автоматизации. [Playwright](https://playwright.dev/docs/locators?utm_source=chatgpt.com)

Однако семантические локаторы тоже могут перестать работать при изменении текста, доступных ролей или структуры страницы.

Поэтому LLM полезнее применять как механизм восстановления, а не замену всем существующим методам извлечения.

## 3. Интерактивный карьерный агент — это следующий уровень

Здесь появляется твоя идея Dots.

Я бы разделил сбор вакансий и интеллектуальную работу с ними.

**Сборщик вакансий** отвечает за полноту, свежесть, дедупликацию и корректность данных.

**Career Agent** отвечает за понимание карьерной цели и взаимодействие с пользователем.

Например, ты пишешь агенту:

> Проверь новые вакансии Яндекса, Сбера и Авито. Найди позиции, связанные с обучением генеративных моделей. Не предлагай мне RAG-интеграции и обычный Python Backend. Выдели вакансии, где мои навыки наиболее близки к требованиям. Для пяти лучших подготовь отклики.

Агент выполняет запрос, используя уже собранную базу.

Если обнаруживает потенциально интересную вакансию, по которой недостаточно информации, он может самостоятельно открыть оригинальную страницу и дополнить сведения.

Если ты одобряешь отклик, агент подготавливает форму на карьерном сайте, выбирает подходящую версию резюме и заполняет необходимые поля. Финальная отправка — после подтверждения.

**Это уже полноценная агентная система, а не поисковый интерфейс над вакансиями.**

Для неё потребуется хранить состояние: какие вакансии просмотрены, какие отклонены, куда отправлено резюме, какие ответы получены и что изменилось с момента предыдущей проверки.

## 4. А стоит ли использовать непосредственно OpenAI Dots?

Здесь есть важное различие.

**OpenAI Dots — готовый продукт для персональной агентной работы, а не специализированный фреймворк краулинга.**

Согласно актуальной документации, Dots может работать с подключёнными приложениями, использовать облачный компьютер и делегировать задачи в Codex. Однако у проактивного исследования существуют ограничения: в этом режиме нельзя непосредственно управлять браузером или компьютером. [OpenAI Help Center](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot?utm_source=chatgpt.com)

Поэтому я бы не делал Dots технологической основой сборщика вакансий.

Вместо этого разумнее разработать собственного агента поверх браузерной автоматизации и LLM, а Dots, если он тебе доступен, использовать как внешний управляющий интерфейс.

Для такого решения уже существует [OpenAI Computer Use API](https://developers.openai.com/api/docs/guides/tools-computer-use), но браузерные действия необходимо ограничивать, проверять и защищать от prompt injection. [OpenAI Developers](https://developers.openai.com/api/docs/guides/tools-computer-use?utm_source=chatgpt.com)

Для эксперимента можно взять сохранённые версии страниц, искусственно изменить их структуру и сравнить обычный парсер с гибридной системой.

Оценивать стоит долю успешно извлечённых вакансий, полноту полей, время восстановления, стоимость LLM-вызовов и частоту ошибочных восстановлений.

И только после такого эксперимента масштабировать решение на другие сайты.

## 6. Самое важное: у тебя появляется возможность построить агентную инфраструктуру

Я вижу здесь два относительно самостоятельных направления.

Первое — **Adaptive Web Extraction**: универсальный движок, который извлекает структурированные данные из веб-интерфейсов и адаптируется к изменениям их структуры.

Второе — **Personal Career Agent**: система, которая использует эти данные для персонального поиска работы, подготовки откликов и сопровождения карьерной воронки.

Второе направление непосредственно решает твою текущую задачу. Первое интересно и как отдельная инженерная разработка.

Причём в дальнейшем ты сможешь подключать не только HH и карьерные сайты компаний, но и другие разрешённые источники вакансий, не переписывая всю систему.

### Мой вывод

**Да, делать AI-агента имеет смысл. Но я бы начал не с автономного агента, который бесконечно ходит по сайтам, а с интеллектуального слоя над существующей инфраструктурой.**

Тебе не нужен LLM, который ежедневно выполняет тысячи однотипных браузерных операций.

Тебе нужен агент, который:

1. Понимает, какую информацию требуется получить.
2. Выбирает наиболее надёжный и дешёвый способ получения данных.
3. Обнаруживает, когда обычная автоматизация перестала работать.
4. Самостоятельно предлагает или выполняет проверяемое восстановление.
5. Выполняет сложные интерактивные действия, когда простые механизмы недостаточны.

**Именно четвёртый пункт я считаю наиболее интересным с технической точки зрения.**

По существу, ты можешь перейти от системы с множеством поддерживаемых вручную парсеров к архитектуре, в которой LLM становится механизмом адаптации к изменяющимся внешним интерфейсам.

Это гораздо более обоснованное применение агентного ИИ, чем попытка заменить каждый HTTP-запрос дорогостоящим браузерным рассуждением.
