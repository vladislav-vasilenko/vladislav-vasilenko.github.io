# Гибридный сбор вакансий

Обновлено: 2026-10-20. Реализация использует существующие SQLite, ArchiveStore, browser_commands и discovery_runs. Старый Chroma pipeline и модельные вызовы не запускаются сборщиком.

## Как работает

В настройках сбора доступны четыре порядка: Python → Chrome, Chrome → Python, только Python, только Chrome. В текущей пользовательской конфигурации выбран Python → Chrome; остальные настройки, включая разрешение платного ранжирования, сохранены. Старые запуски сохраняют свои настройки.

Для корпоративных страниц Python сначала читает публичное HTML конкретной вакансии; для выдачи использует существующие специализированные scrapers. Если чтение завершилось ошибкой, вернуло непроверенную пустую выдачу или неполные описания, очередь создаёт одну резервную попытку другим способом. У неё новый идентификатор квитанции; прежние результаты и история сохраняются. Бесконечного переключения нет.

| Источник | Python | Chrome |
| --- | --- | --- |
| Yandex, Sber, Avito, Ozon, T-Bank | Существующие парсеры; поддержанные фильтры | Имеющиеся DOM-адаптеры и выданные разрешения |
| HH | Не используется для авторизованного сбора | Существующее расширение |
| Google, Meta | Существующие парсеры | Резервного адаптера пока нет |

Неподдержанные Python-фильтры передают чтение Chrome. Фильтры не отбрасываются молча. Python не обновляет приватное HH-резюме. Google/Meta не считаются проверенными в авторизованном Chrome; активность остаётся неизвестной без распознанного источника подтверждения.

## Хранение и ограничения

Python выполняется отдельным процессом с дедлайном 75 секунд и лимитом 100 записей. Ему не передаются CV, API-ключи, сессии или доступ к рабочей базе. Родитель проверяет источник, ID, качество текста и сохраняет разрешённые поля через ArchiveStore.sync. Отмена после чтения предотвращает запись. Пустая выдача после исключения не подтверждает отсутствие вакансий и не закрывает старые записи.

Сбор из веб-сервиса через Chrome теперь передаёт описания непосредственно в SQLite, а большой набор держит только в памяти текущего чтения. Квитанция при переполнении local storage использует session storage. Состояние на 20.10: автономный popup ещё использовал прежний локальный кэш. В реализации от 22.10 ниже popup при подключённом сервисе также передаёт записи прямо в SQLite. Нужен worker 0.11.22+; host permissions не расширялись.

Пауза/отмена и история остаются в существующих таблицах. Следующий transport не стартует после отмены. Счётчики Python и Chrome разделены в health. UI задачи показывает Python для исполняемой Python-команды.

## Проверка

На реальном запуске через очередь Python прочитал Avito 19450 за 0,8 с: 4512 символов, full, active; запись подтверждена в SQLite. Платных API: 0. Отчёт: `/Users/vladmac/Documents/AI Vacancies Replies/hybrid-collection-smoke-2026-10-20.json`.

Отдельная ограниченная HTTP-проверка: Yandex — 1 полное описание, Avito — 1 полное описание, Ozon — таймаут, Sber search — динамическая страница без извлечённых вакансий. Это проверка выбранных URL, не измерение покрытия всего рынка. Google/Meta вживую в этой итерации не проверялись.

Автотесты проверяют оба направления fallback, новые receipt IDs, сохранение частичных данных, pause/cancel, корректный checkpoint discovery, разделение health, запрет чужих ID/источников, короткие тексты и quota-safe поток в SQLite. Они используют временную базу, без браузера и моделей.

Итог проверки: 406 Python-тестов в изолированной копии и 362 JS-теста прошли. Для исчезнувшего Chrome-worker добавлен таймаут чтения: после 5 минут без heartbeat задача завершается с диагностикой и переходит к резервному способу, если он доступен.

## Что ещё проверить

После перезагрузки Chrome-расширения проверить полный запуск HH и корпоративную выдачу. Последний наблюдавшийся массовый запуск HH до обновления упал на kQuotaBytes quota exceeded. Подключённый heartbeat сам по себе не означает успешный сбор. Не очищать старый кэш без проверки его синхронизации и отдельного запроса пользователя.

## Рефакторинг надёжности — 22.10.2026

Реализованы `collection_policy.py` (единая политика), `collection_backfill.py` (дозагрузка архива) и общий `collection-storage.js` для popup и очереди сервиса.

- Для публичной детали: HTTP → Playwright с теми же DOM-адаптерами, что у расширения → авторизованный Chrome. HH остаётся в авторизованном Chrome без передачи его сессии Python.
- Дозагрузка обходит сохранённые ссылки с неполным текстом независимо от поисковой выдачи. SQLite хранит запись на вакансию, команду, число попыток, отсрочку и причину. Окно ограничено тремя заданиями и одним на источник. Повторный старт активного запуска идемпотентен.
- Поддержаны пауза, продолжение и отмена. Временные ошибки повторяются с задержкой и лимитом. CAPTCHA/вход/изменённая разметка приостанавливают весь источник; HTTP 429 включает общий cooldown. Успешно прочитанное сохраняется независимо от ошибок других сайтов.
- Сбор не вызывает embeddings, Luna, генерацию писем или отправку откликов. Полный текст и подтверждённое закрытие не заменяются более слабым наблюдением.
- Ручной popup при доступном сервисе тоже сохраняет данные сразу в SQLite; статусы используют session storage при переполнении local. Автономный режим без сервиса сохраняет прежний локальный кэш, а сбой хранения не выдаётся за успех.
- Фоновый HH poll сначала проверяет очередь без открытия страницы переговоров. Для реального автоматического sync используется одна временная вкладка с дедлайном 110 секунд и ограничением чтения DOM. Истёкший sync становится ошибкой с backoff. Задачи сбора используют отдельную вкладку чтения и освобождают только собственные блокировки.
- `hh-dom-v2` различает неизвестную разметку и подтверждённо пустую выдачу; видимая кнопка входа в шапке не блокирует чтение общедоступной вакансии.
- Дозагрузка требует протокол расширения 2 (0.11.22+). Старый worker не заберёт эти задания. Нужно перезагрузить расширение, а не только обновить открытую страницу HH.

Проверки: 421 Python-тест в изолированной копии и 374 JS-теста прошли. Реальный Playwright DOM read Avito 19450: full, 4483 символа, 8,29 секунды. Поведение всех сайтов в авторизованном Chrome этим тестом не подтверждается.

В интерфейсе: Вакансии → «Полные описания · дозагрузка архива» → «Дозагрузить полные описания». Состояние доступно через `collection_backfill`, запуск — `collection_backfill_start`, управление — `collection_backfill_control` существующего workflow API. Все операции требуют штатного доступа к локальному сервису.

[LLM-восстановление адаптеров](../ideas/llm-adapter-repair.md) пока записано как отдельная идея с проверкой, версионированием и согласованием расходов; этот рефакторинг его автоматически не запускает.


### Проверка текущего запуска

Одиночное чтение HH 137802817 через общую очередь завершилось `complete`: полное описание сохранено. Дозагрузка запущена из веб-интерфейса на 974 неполных записях. В начале проверки подтверждены 11 новых полных описаний (4 HH, 3 Ozon, 4 T-Bank); это промежуточное состояние, а не завершение всей очереди.

Над блоком подробностей показывается прогресс: обработано / всего, процент, отдельно загруженные описания, чтение, ожидание, повторы и необходимость проверки. Счётчики берутся из SQLite каждые 5 секунд, в том числе при свёрнутых подробностях. Повторное открытие страницы восстанавливает состояние. «Обработано» включает закрытые и проблемные записи; это не число успешно загруженных описаний.

Для переполненного Chrome storage local очередь версий и служебные настройки архива имеют долговечный резерв IndexedDB. Несинхронизированные записи не удаляются; квитанции сервера очищают только подтверждённые версии. Если оба хранилища недоступны, ошибка явная. Восстановление всего архива обратно в кэш Chrome может по-прежнему не поместиться: в таком случае SQLite не меняется, предлагается использовать веб-сервис.
