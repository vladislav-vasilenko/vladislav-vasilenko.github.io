# ADR 0004 — Локальная доступность и отдельное решение о 24/7

Дата: 19.10.2026. Статус: локальный режим сохраняется; always-on deployment отложен до требований/оценки.

## Контекст

[telegram_recruiter.run](../../../telegram_recruiter.py), локальный API, SQLite и Chrome работают на ноутбуке. macOS может кратко просыпаться в DarkWake. 19.10.2026 журнал показал wake в 10:29:41/10:40:29, а локальные outbox receipts — sent в 10:29:46/10:40:35. Discovery при этом завершился по времени. Доставленное сообщение не доказывает завершённый crawl.

Есть отдельный GitHub Actions public scraper, но он не получает автоматически личный SQLite и не управляет текущим Chrome/Telethon. Перенос бота на сервер сам по себе не даёт ему доступ к локальной браузерной сессии.

## Решение

На ближайшем этапе улучшить existing scheduler/queue: stale heartbeat → «Ждём Chrome», отсчёт активного выполнения отдельно от ожидания, сохранение partial, catch-up после сна и dedupe уведомлений. Настройки питания, автозапуск OS и удалённые сессии не менять скрыто.

Если требование — гарантированные подборки дважды в сутки при выключенном ноутбуке, зафиксировать отдельный deployment ADR: один always-on узел для разрешённого discovery и бота, privacy/auth, ownership данных, резервное копирование и синхронизация. Приватные сессии HH/Telethon и реальные отправки — отдельные границы согласования. SQLite не делать общей writable БД на сетевом диске.

## Последствия

Локальный продукт должен честно показывать зависимость от доступности Chrome. До always-on решения обещание «автономно 24/7» некорректно. MCP stdio также требует работающего локального процесса/хоста. Инфраструктурное усложнение допустимо по подтверждённому SLA, а не как условие самого архитектурного аудита.
